# Integration & Testing Issue Log — Weeks 6–7

Tracks issues found and resolved (or still open) while integrating,
testing, and refining the pipeline. Format: found → cause → resolution/status.

| # | Issue | Found During | Cause | Status |
|---|---|---|---|---|
| 1 | Multicollinearity between `previous_no_shows` and engineered `no_show_rate_history` (0.79 correlation, contradictory coefficient signs) | Error analysis of Week 5 baseline (§9 of PIPELINE.md) | Raw history counts and the engineered ratio were both left in the feature matrix in Week 5 | **Resolved** — `previous_appointments`/`previous_no_shows` dropped from the feature matrix in `build_features.py` |
| 2 | `validate_training_inputs` crashed on plain Python lists (only worked with numpy arrays/Series) | Writing `tests/test_integration.py` | `pd.unique()` doesn't accept a plain `list` | **Resolved** — wrapped with `np.asarray()` |
| 3 | Week 5 inference picked "latest file matching a fixed prefix" — would silently load a losing candidate once multiple models exist in `models/` | Reviewing Week 5 `score.py` for integration gaps (Task 1) | No concept of an "approved"/"recommended" model, only a filename pattern | **Resolved** — inference now looks for `candidate_recommended_*` specifically; falls back to the Week 5 baseline artefact with a logged warning if none exists |
| 4 | No validation of model output before handing it to a downstream consumer (dashboard/reminder workflow) | Task 5 (validation checks for pipeline inputs/outputs) | Week 5 scope was "prove it runs", not "prove it's safe to consume" | **Resolved** — `validate_scores()` checks probability range, NaNs, row-count integrity, duplicate/missing IDs, valid risk tiers |
| 5 | Feature-column mismatch between a trained model and a batch being scored would previously surface as an opaque sklearn shape error deep in `model.predict()` | Task 3 (data processing / model input-output compatibility) | No explicit contract check before calling the model | **Resolved** — `validate_feature_matrix_contract()` checks the exact column set before scoring |
| 6 | `config.yaml` existed but was not actually read by any module | Carried over from Week 5's own "Implementation Issues" section | Deferred in Week 5 due to time | **Resolved** — `src/config.py` added; `train.py`/`score.py` now call `get_config()` |
| 7 | No logging — every module only used `print()` | Task 10 (add logging/execution information) | Not prioritised in Week 5 | **Resolved** — shared `get_logger()` in `src/config.py`, used in `train.py`/`score.py`. `validate.py`/`clean.py`/`build_features.py` still use `print()` in their `__main__` blocks (acceptable — they're inspection scripts, not pipeline stages that run unattended) |
| 8 | Marginal, near-zero performance gain from feature refinement and the RandomForest candidate (ROC-AUC 0.6733 → 0.6734) | Model comparison (Task 8) | Likely a ceiling effect of the available features on this dataset, not a modelling-technique problem | **Open** — flagged for the Data Science track; richer features (e.g. from the Data Analytics track's Week 6 advanced analysis) may be needed for a meaningful jump, not just algorithm swaps |
| 9 | Categorical encoding used `pd.get_dummies` + `reindex`, not a saved/fitted encoder object | Carried over from Week 5 | Deferred in Week 6 — acceptable for this dataset's fixed category set, thought to be low-risk | **Resolved in Week 7** — see #11 below, which is what this risk actually turned into in practice |
| 10 | No fairness/bias testing on demographic features (`gender`, `age`) | Carried over from Week 4/5 risk register | Not yet started | **Open** — recommended before any model is promoted beyond "candidate" |
| 11 | **[Week 7, critical]** A single-row (or otherwise small/skewed) batch produced a feature matrix with a completely different, smaller column set than training (~9 columns instead of ~30) | Deliberate edge-case probing before writing formal Week 7 tests (Task 3/9) | `pd.get_dummies` only creates one-hot columns for category values actually present in the DataFrame passed to it — a batch missing some categories silently produces fewer columns. The Week 6 `reindex(fill_value=0)` safety net masked the crash but meant a real category could be silently scored as the reference/baseline category | **Resolved** — added `fit_feature_params()` to compute fixed category levels once from the training set; `build_feature_matrix()` now applies them via `pd.Categorical` before encoding, so column shape is identical regardless of batch size. Regression tests: `test_single_row_batch_produces_full_column_set`, `test_skewed_batch_all_same_category_produces_full_column_set` |
| 12 | **[Week 7, critical]** `long_lead_time`'s threshold was recomputed as the 75th percentile of whatever batch was passed in — a single-row batch's own value is trivially its own 75th percentile, so `long_lead_time` was **always 1** for any single-appointment batch regardless of the appointment's actual lead time | Same edge-case probing session as #11 | Threshold computed from `df` (the batch) instead of a fixed, fitted reference value — a train/serve skew bug | **Resolved** — threshold now fit once from the training set (part of `fit_feature_params()`) and reused unchanged at inference. Regression test: `test_long_lead_time_threshold_is_fixed_not_recomputed_per_batch` |
| 13 | Dropping a required column entirely (e.g. `distance_to_clinic_km`) raises a raw `KeyError` deep inside `clean_appointments()` rather than a clear, actionable error | Week 7 edge-case testing (Task 9 — invalid/unexpected input scenarios) | `clean.py` assumes the validated schema is already correct and doesn't re-check column presence itself | **Open** — documented and tested (`test_missing_required_column_raises_clear_error` asserts the current `KeyError` behaviour so a future fix doesn't silently change behaviour unnoticed); a clearer error message is a good Week 8 cleanup, not urgent since `validate_schema()` upstream already catches missing columns in the normal pipeline path |
